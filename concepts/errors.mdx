Every error response from the MarketBox API uses the same envelope.

## The envelope

```json
{
  "code": "NOT_FOUND",
  "message": "Booking not found",
  "statusCode": 404,
  "requestId": "3f7c1a9e-5b2d-4e8a-9f01-2c6d8b4a7e13"
}
```

| Field        | Meaning                                                                     |
| ------------ | --------------------------------------------------------------------------- |
| `code`       | Stable, machine-readable identifier. Use this for branching.                |
| `message`    | Human-readable explanation. May change over time.                           |
| `statusCode` | The same status as the HTTP response — included for clients that hide it.   |
| `requestId`  | Unique id for this request. Also returned in the `X-Request-Id` header.     |

<Tip>
  Always log `requestId` alongside the request you made — it's what
  MarketBox support uses to look up a single call in our logs.
</Tip>

### Conflict bodies carry extra fields

Supplier-time conflicts and hold-lifecycle failures use the same four envelope
fields as every other error — plus extras that tell you how to recover.

A **slot conflict** (`409 SLOT_HELD` / `SLOT_BOOKED`, from any booking or hold
route) adds `conflicts[]` and `hint`:

```json
{
  "code": "SLOT_HELD",
  "message": "Supplier time is not available: HOLD resv_01kv8p2… (2026-07-15T14:00:00Z–15:00:00Z)",
  "statusCode": 409,
  "requestId": "9d4b6f21-8a3c-4f7e-b1d5-6e2a9c0f4b87",
  "conflicts": [
    {
      "claimType": "HOLD",
      "supplierId": "sup_01kv60qgnef2kt3pvqgwmkbzfr",
      "startUtc": "2026-07-15T14:00:00.000Z",
      "endUtc": "2026-07-15T15:00:00.000Z",
      "reservationId": "resv_01kv8p20m1gnqvxl92xln6awk8",
      "bookingId": null,
      "heldUntil": "2026-07-15T13:35:00.000Z"
    }
  ],
  "hint": "This time is held (reservation resv_01kv8p2…). Convert the hold via POST /v1/projects/{projectId}/holds/{reservationId}/convert, or release it…"
}
```

`conflicts[]` names **what** is blocking you (a `reservationId` for a `HOLD`, a
`bookingId` for a `BOOKING`) and `hint` names **what to do next** — both are
meant to be read programmatically.

A **hold-lifecycle** failure (`409`, see the table below) is the plain envelope:

```json
{
  "code": "HOLD_EXPIRED",
  "message": "Reservation resv_01kv8p2… expired at 2026-07-15T13:35:00.000Z",
  "statusCode": 409,
  "requestId": "5a1e8c34-2f6b-4d9a-8c17-3b5e7a1d9f42"
}
```

## Status codes

| Status | When you'll see it                                                                                 |
| ------ | -------------------------------------------------------------------------------------------------- |
| `400`  | The request is malformed: invalid JSON, invalid query parameters, a violated business invariant.   |
| `401`  | The user token on an end-user route (`/clients/me`, `/suppliers/me`) is missing, malformed, invalid or expired — sign the person in again. Also the beacon's publishable key, when it is missing or not live. A missing or unrecognised **API key** is `403`, not `401`. |
| `403`  | The `x-api-key` header is missing or the key isn't recognised — rejected at the edge, before any scope check runs — or the key is valid but its `projectScope` does not allow the `{projectId}` in the URL, or it lacks the capability the route needs. On an end-user route, also: the signed-in person isn't an `ACTIVE` member of the project holding the route's permission. |
| `404`  | The resource you targeted doesn't exist (or has been soft-deleted).                                |
| `409`  | Version conflict on an optimistic update, the supplier's time is already booked or held, capacity exceeded, or duplicate registration. |
| `413`  | The request body is too large — on the site-events routes, more than 256 KB per batch or 64 KB per beacon. Nothing was read. |
| `422`  | The request is well-formed but asks for something the data cannot support: a package plan that no availability can fill, a line the service is not sold as, or a credit treatment for a booking with no credit. Nothing was written. |
| `429`  | Too many requests from this key. Today only the site-events routes rate-limit. Retry after the `Retry-After` header. |
| `503`  | A dependency was down and nothing was recorded. Retry after the `Retry-After` header. |
| `5xx`  | Something went wrong on our side. Safe to retry idempotent requests with backoff.                  |

## Common error codes

| `code`                                  | Status | Notes                                                                                   |
| --------------------------------------- | ------ | --------------------------------------------------------------------------------------- |
| `VALIDATION_ERROR`                      | 400    | Request body or query failed schema validation. `message` names the field.              |
| `BAD_REQUEST`                           | 400    | Generic client-input failure covering several situations: an illegal status transition (e.g. nothing leaves `CANCELLED`; the `message` names the booking's current status), a mismatched currency between an order and an item you're adding to it, an offering that isn't `ACTIVE`, an unparseable pagination `cursor`, and other malformed input. `message` names the specific problem. |
| `HTTP_ERROR`                            | 400, 401 | A request refused before its route ran. `401` on an end-user route: a missing or malformed `Authorization` header, or a user token that is invalid or expired — sign in again. `400`: a body that isn't valid JSON. |
| `UNAUTHORIZED`                          | 401    | On an end-user route, a user token that names no user — and, once enforced, a token issued to another client. See [End-user authentication](/concepts/end-user-authentication#where-the-user-token-comes-from). A missing or unrecognised **API key** is `FORBIDDEN`. |
| `FORBIDDEN`                             | 403    | API key is missing, isn't recognised, or cannot access this project. The first two are rejected at the edge before the request reaches the application, so `message` — not `code` — is what distinguishes them. On an end-user route, also "No active membership on this project" or "Insufficient permissions for this action". On `POST .../events`, a key without `events:write`. |
| `CAPABILITY_NOT_GRANTED`                | 403    | Your API key lacks **Standard API access** (`*`): its capabilities are empty or name only site events. Checked before the project or the user token. A project admin grants it on the Application. See [Capabilities](/concepts/authentication#capabilities). |
| `ACTING_ROLE_NOT_HELD`                  | 403    | An end-user request sent `X-MB-Acting-Role` naming a role the signed-in person doesn't hold. Drop the header. |
| `MEMBERSHIP_INACTIVE`                   | 403    | `POST .../clients/me` (onboarding) for a person whose access the business removed. Nothing was read or linked. The client asks the business to invite them again. See [Build a booking flow](/guides/booking-flow-auth#onboard-the-client). |
| `FIELD_NOT_SELF_EDITABLE`               | 403    | `PATCH .../suppliers/me` named a field only the business may change (`active`, `email`, `externalId`, `externalData`, `maxTravelTime`, `defaultLocale`). The whole body was refused. See [Build a supplier portal](/guides/build-a-supplier-portal#edit-the-profile). |
| `INSIGHTS_DISABLED`                     | 403    | The project has switched off this supplier insight (demand, or search). Hide the insight in your portal. |
| `NOT_FOUND`                             | 404    | Resource doesn't exist or has been soft-deleted. Also returned for a `clientId` or `supplierId` in the request body that belongs to a different project — never a `403`, so a foreign id is indistinguishable from a missing one. |
| `VERSION_CONFLICT`                      | 409    | Concurrent modification — re-read the resource and try again.                           |
| `CONFLICT`                              | 409    | Generic write conflict covering situations like a booking that's already at capacity, or a client that's already registered as a participant on it. `message` names the specific problem. |
| `SLOT_BOOKED`                           | 409    | The supplier's time is already taken by a confirmed booking. `conflicts[]` names the `bookingId`. Not retryable — search availability again. |
| `SLOT_HELD`                             | 409    | The supplier's time is claimed by a live hold — often **your own**. `conflicts[]` names the `reservationId`; convert it instead of booking directly. See [Hold slots during checkout](/guides/hold-slots-for-checkout#handling-a-held-slot). |
| `OCCUPANCY_CONTENTION`                  | 409    | Too many concurrent writes on one supplier's day; the internal retry gave up. **Retryable** — resend after a short backoff. |
| `ORDER_ITEM_BUSINESS_MODEL_MISMATCH`    | 400    | A booking line names a `businessModelType` its order item is not sold as, such as `PACKAGE` against a `SINGLE_SESSION` item. Send the kind the order item was sold as. See [Bookings](/resources/bookings#creating-a-booking). |
| `TAX_MISMATCH`                          | 400    | You sent `tax` on `PATCH .../orders/{orderId}`, and it is not both the tax the lines compute and the tax the order stores — or the order has lines in a different currency. Nothing was written. Omit `tax`: the platform computes it. See [Orders](/resources/orders#updating-an-order). |
| `ORDER_NOT_SETTLED`                     | 409    | You asked `POST .../orders/{orderId}/status` for `PAID`. An order becomes `PAID` only when its ledger covers its total. Record the payment instead of retrying. See [Orders](/resources/orders#settling-an-order). |
| `TRANSACTION_IDEMPOTENCY_RECORD_MISSING` | 409   | An `idempotencyKey` matched an earlier recording whose row could not be read back. **Terminal** — do not retry. Re-read the order's transactions and contact support with the `requestId`. |
| `NO_SESSION_CREDIT`                     | 422    | `creditTreatment` was sent when cancelling a booking that holds no package credit. Nothing was cancelled. Resend without `creditTreatment`. |
| `SERVICE_NOT_SOLD_AS`                   | 422    | An order line implies a rate the service does not actively sell, such as a `SINGLE_SESSION` line on a service with no active `SINGLE_BOOKING` rate. Nothing was written. See [Orders](/resources/orders#creating-an-order). |
| `PAYLOAD_TOO_LARGE`                     | 413    | A site-events batch over 256 KB, or a beacon over 50 events or 64 KB. Nothing was read. Send fewer events per request. |
| `RATE_LIMITED`                          | 429    | More than about 50 site-events requests a second from this key (bursts of 100). Retry the same batch after `Retry-After`. |
| `SERVICE_UNAVAILABLE`                   | 503    | MarketBox couldn't check or record a site-events batch. Nothing was recorded. Retry the same batch after `Retry-After`. |

The exact list of codes is also captured in
[`/v1/openapi.json`](/api-reference/introduction). New codes may be added
over time; treat unknown codes as the generic class implied by the HTTP
status.

## Hold and slate codes

These come from the hold endpoints (`POST /holds`, `/holds/{reservationId}/convert`)
and the slate-based booking routes. Full walkthrough in
[Hold slots during checkout](/guides/hold-slots-for-checkout#troubleshooting).

| `code`                       | Status | What it means                                                                                              | What to do                                                                                             |
| ---------------------------- | ------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `MISSING_BOOKING_TZ`         | 400    | The held interval carries no `bookingTz` and no location to derive one from.                               | Send `bookingTz` (IANA, e.g. `America/Toronto`) on every entry in `intervals[]`. It is required.        |
| `UNSUPPORTED_SKU_TYPE`       | 400    | The order item you're converting against is a `SUBSCRIPTION`, `MEMBERSHIP`, or `DEPOSIT`.                   | Convert against a `PACKAGE` or `SINGLE_SESSION` item. Nothing is wrong with the hold.                   |
| `INVALID_ORDER_REFERENCE`    | 400    | The `orderId` doesn't exist in this project.                                                                | Check the id and the project.                                                                           |
| `HOLD_EXPIRED`               | 409    | You converted after `heldUntil`. Expiry is lazy — the hold simply stopped blocking anyone.                  | Re-hold the time and convert sooner. Someone else may have taken it.                                    |
| `RESERVATION_NOT_FOUND`      | 409    | No such `reservationId` in this project. (`GET /holds/{id}` returns `404 NOT_FOUND` instead.)               | Don't retry. Place a new hold.                                                                           |
| `RESERVATION_NOT_HELD`       | 409    | The hold is already `CONVERTED` or `RELEASED`.                                                              | If `CONVERTED`, re-read the hold — your bookings already exist. Converting is idempotent, not repeatable. |
| `RESERVATION_FORBIDDEN`      | 409    | The `heldBy` you sent doesn't match the hold's owner.                                                       | Send the same `heldBy` used to create the hold (typically your checkout session id).                    |
| `RESERVATION_MULTI_INTERVAL` | 409    | You converted a multi-interval hold against a `SINGLE_SESSION` order item.                                  | Use a `PACKAGE` order item, or hold exactly one interval.                                               |
| `SLATE_NOT_FOUND`            | 409    | The `slateId` no longer exists.                                                                             | Re-run `POST /availability/package-slate` and hold the fresh slate.                                     |
| `SLOT_NOT_FOUND`             | 409    | One or more `slotIds` no longer exist.                                                                      | Same — regenerate the slate.                                                                            |
| `EMPTY_SLATE`                | 409    | The slate resolved to zero slots, or you sent none of `intervals` / `slateId` / `slotIds`.                  | Send exactly one of the three.                                                                          |
| `SUGGESTION_EXPIRED`         | 409    | The underlying suggestion aged out before you booked it.                                                    | Re-run availability.                                                                                    |
| `SLOT_NOT_BOOKABLE`          | 409    | The slot resolved but can no longer be booked.                                                              | Re-run availability.                                                                                    |
| `LOCATION_UNRESOLVABLE`      | 409    | No supplier travel zone covers the requested coordinates.                                                   | The supplier doesn't serve that address. Pick another supplier or location.                             |

<Warning>
  A `404 NOT_FOUND` with the message **`Location stz_… not found`** on convert
  is not a missing record — it means the hold carried a travel-zone id
  (`stz_…`) under `locationType: "PHYSICAL"` (or with no `locationType` at
  all), so it was looked up in the wrong table. Re-hold with
  `locationType: "TRAVEL_ZONE"` plus `latitude`, `longitude`, and `address`.
  See [Hold slots during checkout](/guides/hold-slots-for-checkout#a-travel-zone-checkout-end-to-end).
</Warning>

## Supplier booking codes

These come from the supplier plane's booking routes: cancel, reschedule and the
attendance report. Full walkthrough in
[Build a supplier portal](/guides/build-a-supplier-portal#when-a-change-is-refused).

| `code`                           | Status | What it means                                                                 | What to do                                                   |
| -------------------------------- | ------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `PARTICIPANT_ACTION_DISABLED`    | 403    | The booking's service doesn't let suppliers cancel (or reschedule).            | Hide the action. The supplier contacts the business.         |
| `BOOKING_NOT_SCHEDULED`          | 409    | The booking is no longer `SCHEDULED`.                                          | Re-read the booking. Don't retry.                            |
| `NOTICE_WINDOW_PASSED`           | 409    | Too close to the start to change it.                                           | Don't retry. The supplier contacts the business.             |
| `NEW_START_INSIDE_NOTICE_WINDOW` | 422    | Reschedule only: the new time is itself inside the notice window.               | Pick a later time.                                           |
| `SLOT_UNAVAILABLE`               | 409    | Reschedule only: the new time is outside working hours, in blocked time or overlaps another booking. | Pick another time.                    |
| `SLOT_UNVERIFIABLE`              | 409    | Reschedule only: availability couldn't be checked, so nothing changed.          | Try again later, or contact the business.                    |
| `REPORT_ALREADY_EXISTS`          | 409    | A different attendance answer is already on file.                               | Show the answer on file. Don't retry.                        |
| `BOOKING_ALREADY_SETTLED`        | 409    | The booking is already settled.                                                 | Don't retry.                                                 |
| `BOOKING_NOT_REPORTABLE`         | 422    | The booking is cancelled, or hasn't ended yet.                                  | Report after the booking ends.                               |

## Validation errors

For schema validation failures, `message` names the offending field:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "bookingEndUtc must be strictly after bookingStartUtc",
  "statusCode": 400,
  "requestId": "7c3f0a5d-9b2e-4a68-9d14-5f8c2b6e0a91"
}
```

We do **not** return a nested errors array — one error per response. If
multiple fields are wrong, you'll fix the first, retry, and surface the
next.

## Retry guidance

- **`4xx`** — never retry blindly. Fix the request and try again.
- **`409 VERSION_CONFLICT`** — re-read the resource (its `version` field
  has advanced), reapply your patch, and retry.
- **`409 OCCUPANCY_CONTENTION`** — transient contention on a supplier's
  day. Resend the same request with a short, jittered backoff.
- **`409 SLOT_HELD` / `SLOT_BOOKED`** — never retry the same call. The
  response body names the blocking `reservationId` or `bookingId`; convert
  the hold, or pick a different time. See
  [Concurrency](/concepts/concurrency).
- **`409 HOLD_EXPIRED` / `RESERVATION_*`** — never retry. The hold is in a
  terminal state, and retrying cannot move it out of one. Re-hold, or (for
  `RESERVATION_NOT_HELD` on an already-`CONVERTED` hold) re-read it — your
  bookings already exist.
- **`5xx`** — retry idempotent requests (`GET`, `DELETE`, `PATCH` with
  the same body, status changes to the same target) with exponential
  backoff. Avoid blind retries on `POST`, since the original may have
  succeeded.
- **`429 RATE_LIMITED`** and **`503 SERVICE_UNAVAILABLE`** — wait for the
  `Retry-After` header, then resend the same request. On the site-events routes,
  resend the same batch with the same `eventId`s; nothing is counted twice.

## Surfacing errors to support

When opening a support ticket, include:

1. The `requestId` from the failed call.
2. The approximate time (with timezone).
3. The endpoint and HTTP method.
4. The `code` and `message` from the response.

That's enough for MarketBox support to find the exact request in our
logs.
